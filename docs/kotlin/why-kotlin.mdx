# Why Kotlin instead of Java?

:::tip Short answer
Kotlin is usually the better default for modern Android because Android is Kotlin-first, the type system prevents common mistakes, the language expresses intent with less ceremony, coroutines support structured asynchronous work, and existing Java can be retained during incremental adoption.
:::

Java still works and remains supported. The engineering question is which language gives a particular team the best balance of safety, maintainability, ecosystem alignment, build cost, and migration risk.

## 1. Nullability becomes part of the contract

<Tabs>
<TabItem value="java" label="Java">

```java
Integer length = user.getNickname().length(); // may fail at runtime
```

</TabItem>
<TabItem value="kotlin" label="Kotlin" default>

```kotlin
val length: Int? = user.nickname?.length
val displayLength: Int = length ?: 0
```

## 2. Less accidental plumbing

```kotlin
data class UserUi(val id: Long, val name: String)
```

This can generate equality, hashing, `toString`, component functions and `copy`. The advantage is clearer intent—not merely fewer characters.

## 3. Structured asynchronous work

Coroutines let functions suspend without blocking their thread while suspended. Structured concurrency associates child work with an owning scope, giving cancellation and failure defined boundaries.

```kotlin
fun refresh() = viewModelScope.launch {
    val result = repository.refreshUser()
    // update immutable UI state
}
```

:::warning
Coroutines do not make blocking work non-blocking automatically. A blocking call still occupies its thread.
:::

## 4. Incremental interoperability

Kotlin and Java can coexist in one Android module. Add accurate Java nullability annotations, prevent platform types from spreading, and test APIs from both languages when both are consumers.

## Architect decision

Do not rewrite stable Java code solely to change language. Migrate when a new feature, defect risk, maintenance problem or API redesign creates measurable value. Track build time, onboarding, defects and delivery outcomes.

## Interview question

<details>
  <summary>Is Kotlin always faster and completely safe from NPEs?</summary>
  <p>No. Performance depends on generated bytecode, allocations, algorithms and workload. Kotlin can still encounter NPEs through not-null assertions, platform types, Java interoperability, initialization mistakes, or explicit throws.</p>
</details>
